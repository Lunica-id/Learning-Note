### Password Reset

ログイン時等にパスワードを忘れた場合に変更できる機能があるが、この機能は直接的なログイン動作ではないために対策から見落とされがちである

パスワードリセットの脆弱性への対応策

- Emailを送り、そこでパスワードも送る　→ただしメールボックスは永続的に残るものでありそこまでセキュアではないため、その送ったパスワードの有効期限を設定したりすぐさまユーザーにパスワードを変えてもらわなくてはいけない
- ユニークなURLを送り、そこでパスワードのリセットを行ってもらう　→ただしそのURLが単純なものである場合はむしろそこの書き換えのみで不正侵入ができてしまう、そのため予測不可能な文字列を使用したりトークンをチェックし本当に存在するかを確認する

#### Password reset poisoning

Password reset poisoningとは、Host情報を書き換えることでトークンを不正取得しパスワード変更を不正に行うこと

本来であれば、本人がリセット要求をして、本人のメールアドレスにパスワード変更用のURLが届く。その時にtokenも付随しており、そのURLに飛んだ時にtokenがサーバー側に存在するかチェックを行ってはじめてパスワード変更ができる。

不正に行う場合:
まず、攻撃者がパスワードリセット要求をするが、その際にヘッダー内のHostを書き換え自分のサーバーなどにする。
もし攻撃先のサーバーがパスワードリセットURL作成時にHostの内容をそのままtokenとともにURL内に組み合わせる仕組みであった場合、URLはその書き換えられたHost名で作成されてしまう。するとメールを送られたユーザーがそのURLをタッチ/クリックすることでそのまま攻撃者にURLとともに送られ、tokenが攻撃者に知られることなる。またそのtokenを使用して攻撃者がパスワードを設定できてしまう
つまり、Hostの値を過信しているために起きる脆弱性である。

他にも、パスワード変更画面において、usernameを過信することで起こる脆弱性もある
HTMLやHTTPの通信などユーザー側からくるものは基本書き換えられるものとして考える必要がある

#### My understanding

そもそもHostとは、URLにおいて数字ではなく人間が識別しやすいように文字列で書いたものである。基本DNSによって名前解決がされる。
しかしサーバーによっては同じ機械で複数のサービスを提供していることがあり、その場合機械が同じであるためIPアドレスが変わらないため、その後にどこへの問い合わせかを識別する必要がある(virtual host)
そのためヘッダーにHost名を書く必要がある場合もある。

ポートはそもそもSSHやHTTPといった部分のネットワークサービスの違いの識別用
TCPやUDPレベルで使われる
一方HostはHTTPなどのアプリケーション層であり、すでにポートで443などに振り分けられた後にさらに振り分ける
